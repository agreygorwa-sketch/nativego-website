NativeGo — The Database

The database is the memory of the website. It is named nativego_db. It has 8 tables. This page explains each one in plain words.

Database ideas, in plain words

IdeaPlain meaningExample here
TableA list about one thing. Like a sheet in a notebook, with columns across the top and one row per item.users is a table. One row per person.
RowOne item in a table.One row in users is one person: their name, email, password hash, role.
ColumnOne kind of fact about every item.email is a column in users. Every user has an email.
Primary key (PK)The ID number that names one row and no other. It is unique, so the system can always find the exact row.id in users. User 1, user 2, user 3 — never two users with the same id.
Foreign key (FK)A column that holds the ID of a row in another table. It is how tables link to each other.tourist_id in requests holds the id of a row in users. It says which tourist made this request.
RelationshipHow two tables connect. "One to many" means one row in table A links to many rows in table B.One provider has many requests. One tourist writes many reviews.
NOT NULLThis column must always have a value. It cannot be left empty.email in users is NOT NULL. Every account needs an email.
UNIQUENo two rows can have the same value in this column.email is UNIQUE. Two people cannot register with the same email.

The 8 tables

1. users — every person who has an account

One row per person: tourist, provider, or administrator. The role column says which one.

ColumnTypeKeyRule
idINTEGERPKAuto-increment, unique identifier
nameVARCHAR(100)NOT NULL
emailVARCHAR(120)NOT NULL, UNIQUE
password_hashVARCHAR(255)NOT NULL (hashed, never stored plain)
roleVARCHAR(20)NOT NULL, DEFAULT 'tourist', must be tourist, provider, or admin
phoneVARCHAR(20)Can be empty
activeBOOLEANNOT NULL, DEFAULT TRUE (admin sets it FALSE to suspend)
created_atTIMESTAMPNOT NULL, set when the row is created

2. providers — the service profile of a local guide

One row per provider. It links to users by user_id: the person behind the profile. verified is FALSE until the administrator approves the documents (FR-16).

ColumnTypeKeyRule
idINTEGERPKAuto-increment
user_idINTEGERFK → users(id)NOT NULL, UNIQUE — one profile per person
business_nameVARCHAR(150)NOT NULL
categoryVARCHAR(60)NOT NULL (for example Safari Guide, Water Sports)
locationVARCHAR(100)NOT NULL
descriptionTEXTNOT NULL
price_per_dayINTEGERNOT NULL, must be 0 or more (Kenya Shillings)
phoneVARCHAR(20)NOT NULL
verifiedBOOLEANNOT NULL, DEFAULT FALSE — set by admin
average_ratingDECIMAL(2,1)DEFAULT 0.0, kept up to date from reviews
created_atTIMESTAMPNOT NULL

3. requests — a tourist asking a provider for a service

One row per request. It links to the tourist (tourist_id → users) and to the provider (provider_id → providers). The status moves: pending → accepted or declined → completed or cancelled.

ColumnTypeKeyRule
idINTEGERPKAuto-increment
tourist_idINTEGERFK → users(id)NOT NULL
provider_idINTEGERFK → providers(id)NOT NULL
service_dateDATENOT NULL
guestsINTEGERNOT NULL, must be 1 or more
notesTEXTCan be empty
statusVARCHAR(20)NOT NULL, DEFAULT 'pending'
created_atTIMESTAMPNOT NULL

4. payments — money for a request (M-Pesa)

One row per payment. It links to the request (request_id → requests). The M-Pesa receipt is UNIQUE, so one receipt cannot pay twice. Note: payment is a future step — the built system does not take live payments yet.

ColumnTypeKeyRule
idINTEGERPKAuto-increment
request_idINTEGERFK → requests(id)NOT NULL
amountINTEGERNOT NULL, must be more than 0 (Kenya Shillings)
phoneVARCHAR(20)NOT NULL — the M-Pesa phone number
mpesa_receiptVARCHAR(30)UNIQUE, empty until confirmed
statusVARCHAR(20)NOT NULL, DEFAULT 'pending'
created_atTIMESTAMPNOT NULL

5. reviews — what a tourist thought of a provider

One row per review. It links to the provider and the tourist. One tourist can review one provider only once (the pair is UNIQUE). The rating is 1 to 5.

ColumnTypeKeyRule
idINTEGERPKAuto-increment
provider_idINTEGERFK → providers(id)NOT NULL
tourist_idINTEGERFK → users(id)NOT NULL
ratingINTEGERNOT NULL, must be 1–5
commentTEXTNOT NULL
created_atTIMESTAMPNOT NULL
(tourist_id, provider_id)UQUNIQUE pair — one review per tourist per provider

6. messages — chat between people

One row per message. It links to the sender and the receiver (both in users), and to a request when the message is about one.

ColumnTypeKeyRule
idINTEGERPKAuto-increment
sender_idINTEGERFK → users(id)NOT NULL
receiver_idINTEGERFK → users(id)NOT NULL
request_idINTEGERFK → requests(id)Can be empty
bodyTEXTNOT NULL — the message text
is_readBOOLEANNOT NULL, DEFAULT FALSE
sent_atTIMESTAMPNOT NULL

7. favorites — providers a tourist saved

One row per saved provider. The pair (user_id, provider_id) is the key, so a tourist cannot save the same provider twice.

ColumnTypeKeyRule
user_idINTEGERPK, FK → users(id)Part of the key
provider_idINTEGERPK, FK → providers(id)Part of the key
saved_atTIMESTAMPNOT NULL

8. activity_log — a diary of what happened

One row per action: who did it, what they did, which table it touched. The administrator reads this to see what happened on the site.

ColumnTypeKeyRule
idINTEGERPKAuto-increment
actor_idINTEGERFK → users(id)Can be empty
actionVARCHAR(60)NOT NULL (for example LOGIN, VERIFY_PROVIDER)
entityVARCHAR(60)NOT NULL — the table affected
entity_idINTEGERCan be empty
detailTEXTCan be empty
created_atTIMESTAMPNOT NULL

How the tables connect

Read it like a family tree. One user can be one provider. One provider has many requests and many reviews. One request has many messages and one payment. One tourist sends many requests and many reviews.

  • users → providers: one person, one profile.
  • users → requests: one tourist, many requests.
  • providers → requests: one provider, many requests.
  • requests → payments: one request, one payment.
  • requests → messages: one request, many messages.
  • providers → reviews: one provider, many reviews.
  • users → favorites: one tourist, many saved providers.
  • users → activity_log: one person, many logged actions.

The rule that keeps it safe: a review cannot be stored without its provider and tourist, a message cannot be stored without its sender and receiver, and a payment cannot be stored without its request. The foreign keys enforce that.

Source: Table 4.3, Database tables of the NativeGo platform, and the Database Schema document (8 tables, 3NF). The prototype uses SQLite; the production path is PostgreSQL.
